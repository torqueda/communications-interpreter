Communications Interpreter: App Map

A one-page guide to where things live, so you can find the right file for a future change. It works offline and is a snapshot of the code as finished for the hackathon.

What the app is

A small Python web server (FastAPI) and one web page. You upload an official English letter; you get a Spanish translation beside the original, matched highlights, a summary where every point links to its source sentence, and a scam warning when something looks wrong. Nothing is stored.

Four main pieces: the page (static/), the server (app/main.py), the pipeline that does the work (app/pipeline.py with the two AI agents in app/agents/), and the checks written as plain code (app/checks.py).

One action, followed through

You drop medicaid_notice.pdf on the page. This is what happens, in order.

  1. 1 · PageYou drop a file. upload() in static/app.js sends it to the server.
  2. 2 · Serverexplain() in app/main.py receives it and calls the pipeline.
  3. 3 · Codeingest() and split_sentences() read the text and number the sentences. No AI yet.
  4. 4 · AI call 1run_reader() translates, highlights, summarizes, checks for scams, citing sentence numbers.
  5. 5 · AI call 2run_verifier() is a separate reviewer that checks call 1 against the original.
  6. 6 · Codebuild_result() proves cited sentences exist, checks dates, applies the reviewer's verdicts.
  7. 7 · PagerenderResults() draws both letters, the summary, and any warnings.

Blue: in the browser. Orange: an AI call. Plain: ordinary code.

A 3-stop route through the code

This is a reference route, not something you have been walked through.

Stop 1 · The entry point: app/main.py, search async def explain

The upload arrives as UploadFile. The one important line hands the slow work to a worker thread with run_in_threadpool, so two AI calls (30 seconds or more) do not freeze the server. Errors raised anywhere below come back here through pipeline_error_handler and become a short JSON {"code": ...} reply.

Stop 2 · The pipeline: app/pipeline.py, search def run_pipeline

It reads like the list above: ingest, number the sentences, run_reader, reject non-English or non-letters, run_verifier, then build_result. The agents' prompts are the long strings named SYSTEM in app/agents/reader.py and app/agents/verifier.py; the shapes they must return are the Pydantic models in app/models.py (ReaderOutput, VerifierOutput).

Stop 3 · The trust step: app/checks.py, search def build_result

This is the project's core idea in code. _clean_summary drops cited sentence numbers that do not exist and marks the point verified: false. date_appears_in confirms the deadline date really appears in the cited sentence. apply_verifier merges the reviewer's verdicts. Anything not confirmed is shown on the page with a "could not verify" label (unverified in static/i18n.js), never silently trusted.

A practice to reuse: break the AI's output on purpose

What happened here. The goal was a verifier you can trust, but a verifier that says "ok" proves nothing until you have seen it say "not ok". evals/planted_errors.py runs the real Reader, secretly changes a deadline date, a phone number, and one translated sentence, then checks that the real Verifier and code checks flag all three. They did (3 of 3). Separately, tests/test_checks.py and tests/test_verifier.py feed the checks bad sentence numbers and missing verdicts and confirm each becomes "could not verify".

How to apply it elsewhere. Whenever one AI step is trusted to check another, write down the mistake you are afraid of, inject exactly that mistake, and run the check. If it passes the broken version, you have found out before a user did. Keep the injected cases as a script, so you can rerun them after every prompt change.

One run per letter is a spot check, not proof: the AI is not deterministic, so run these a few times and add harder cases.
